# Truehand for Mac

A thin Tauri 2 shell around `truehand serve --app`: no domain logic.

- Starts the server as a daemon in its own session (stdin: token, shell secret, this Mac's approver public key and the revoked passkeys, one JSON line) (closing the window or quitting the shell leaves agents running), or reuses the one it started before. Token and shell secret are generated by the shell, passed on stdin, and kept only in one Keychain item (service `it.spaghetticoders.truehand`, account `app`) together with the server's url and pid. Server log: `~/.truehand/app/serve.log`.
- The Keychain item's ACL lets only this Truehand.app read it without asking (decrypt bound to the app's cdhash, nobody may change the ACL). Anything else, an agent running `security find-generic-password -w` included, gets a visible macOS prompt instead of the secret.
- Before sending the token or the secret anywhere, the shell makes whoever listens on the server's address prove it knows the secret: `POST /api/shell/challenge {nonce}` must answer HMAC-SHA256(SHA-256(shell secret), "truehand-shell-challenge/1\n" + nonce). Nothing answers: a new server is started. Something else answers: nothing is sent and the window says the server is not recognized. Every request the shell makes repeats the check.
- Signs the web view in with `POST /api/login` from Rust and sets the `th_session` cookie natively: the token never reaches JavaScript.
- Once its approver key exists, the shell gives the server its public half (`POST /api/shell/key`, Bearer + shell secret) at every start or reuse and right after creating it: the server keeps it in memory to check intents forwarded to remote machines.
- Tray: Open, Open at Login, Quit (asks whether to stop the server too, with `POST /api/shutdown`; stopping it also deletes the Keychain item). Only if that fails does the shell send SIGTERM, and only to the pid the server announced, while its command and start time are the ones recorded then.

## JavaScript API (window.__TAURI__.core.invoke)

| command | returns | |
|---|---|---|
| `shell_request({ method, path, body })` | `{ status, body }` | adds `X-Truehand-Shell`; only the paths in `src-tauri/src/allow.rs`: the task actions, queued confirmations, pairing and devices, settings, config, activation, `commit-config` and `push-base`, machines, token rotation, and for passkeys `POST /api/passkeys/enroll-code` and `DELETE /api/passkeys/{id}`. Never the anchor requests: only `anchor_passkey` makes them |
| | | for `POST …/commit-config`, and `POST /api/queued/{qid}/confirm` of a queued commit-config, the shell adds `thisMacKey` (this Mac's approver public key, if it exists) so the OS dialog labels each approver as this Mac's key or a foreign one |
| `pick_folder()` | `string \| null` | native folder dialog |
| `start()` | url | starts or reuses the server and signs the web view in again |
| `sign_intent({ projectId, taskId, action, approver })` | `{ intent, format: "es256", sig }` | Touch ID, Secure Enclave key; one at a time |
| `approver_key_fingerprint()` | `string \| null` | this Mac's key fingerprint; null if it has no key yet (never creates one, no Touch ID) |
| `anchor_passkey({ id })` | `null` | Touch ID, Secure Enclave key; makes passkey `id`, waiting for this Mac, an owner of the server; one signature at a time, shared with `sign_intent` |
| `revoke_owner({ passkeyId })` | `null` | Touch ID, Secure Enclave key; revokes passkey `passkeyId` (listed, or a soft revocation) for good on this Mac; one signature at a time |
| `approver_public_key()` | `{ pem, key }` | PEM for `approvers` in `.truehand/config.yaml`; `key` is the fingerprint the server shows next to each approver (first 12 hex of SHA-256 of the SPKI DER), to tell this Mac's key from another under the same name |

`sign_intent` asks the verified server for the intent (`POST …/tasks/{id}/intent`), checks it field by field with the rules of `internal/sign` `Intent.Check`, checks that the server's message is the same bytes it rebuilds, shows action, repo, task and title, branch and the abbreviated plan or commit sha in the Touch ID prompt, and signs those bytes with a P-256 key created in the Secure Enclave on first use (CryptoKit, `.privateKeyUsage` + `.biometryCurrentSet`: Touch ID for every signature, and a new fingerprint makes the key unusable, so register the new public key). The private key cannot leave the Secure Enclave; its wrapped form is in `~/Library/Application Support/it.spaghetticoders.truehand/approver-se.key` (0600) and is useless on another Mac.

`anchor_passkey` is how a phone's passkey becomes the first owner of a server on this Mac: the passkey registered with an enroll code from the shell waits for the Mac (`pending: "mac"`). The shell asks the verified server for the intent (`GET /api/passkeys/{id}/anchor-intent`, with the shell's secret), checks it with the rules of `internal/sign` `ServerIntent.Check` and rebuilds its bytes, then checks it against the server's own replies: action `anchor-owner`, credential `id`, the passkey listed by `GET /api/passkeys` as an owner waiting for this Mac, `server`, `rpId` and the public key in the reply equal to the passkey's (the relying party is the host of the https request, the MagicDNS name with tailscale serve), and with remote access through tailscale serve that address too (`GET /api/settings`), `subject` the sha256 of that passkey's id, key and relying party (`Passkey.Binding`), the key fingerprint the server shows equal to the one the shell computes from the passkey's PEM, and a time within 2 minutes of now. The Touch ID prompt shows the passkey's label, its key fingerprint in groups of four (`abcd ef01 2345`, to compare with the one on the phone), the device that registered it (from the reply) and the server it was registered on. The shell then gives the server this Mac's public key (`POST /api/shell/key`: the key may have been created by this very signature, and the server checks the grant with it) and sends `POST /api/passkeys/{id}/anchor {signed: {intent, format: "es256", sig}}`.

`revoke_owner` makes a revocation durable: a passkey removed only from the server's file (`~/.truehand/app`, the user's) could be put back there by anything running as the user, with its old grant. The shell takes the passkey's label, key and fingerprint from `GET /api/passkeys` (a listed passkey, or a `soft` entry of `revocations`), asks for Touch ID by signing a `truehand-mac-revoke/1` message it does not keep, adds `{credential, public_key_sha256, key, label, time}` (`key`, the fingerprint, only to show) to its list in a second Keychain item (account `app:revoked`, or `test:<home>:revoked`; never deleted with the server's credentials), sends the whole list to `POST /api/shell/revoked` (it replaces the server's, which matches by credential or by key), then, if the passkey is still listed, removes it with `DELETE /api/passkeys/{id}`, which asks on the Mac as every removal does. A server the shell starts gets the list, with this Mac's public key if it exists, in the JSON line on its stdin (`{token, shell_secret, mac_key?, revoked}`, `revoked` always present): until a server has received it from the shell, it trusts no owner, so one started without the shell never brings a revoked owner back. If the Keychain item exists but cannot be read, the server is not started. A reused server already has the list from its start; `POST /api/shell/revoked` only carries updates after `revoke_owner`.

## Build

Needs Go, bun, cargo and Xcode's Swift toolchain.

```sh
make app                # bin/truehand with the web app embedded (repo root)
cd shell
bun install --frozen-lockfile
bun run build           # copies ../bin/truehand as the sidecar, builds Truehand.app and the .dmg
cd src-tauri && cargo test
```

The tests sign with software keys in memory only: no Touch ID, no Keychain. The cross-checks with the Go verifier are driven from Go: `TRUEHAND_SIGN_FIXTURE=<dir>` makes `sign_intent`'s test write what it signed there, and `TRUEHAND_ANCHOR_SERVER=<dir>` makes `anchor::tests::checks_and_signs_replies_from_a_real_server` check and sign the replies of a real `internal/serve` saved in that directory, and `TRUEHAND_REVOKE_SERVER=<dir>` makes `revoke::tests::builds_the_revoked_body_from_a_real_server` build the body for `POST /api/shell/revoked` from one.

Output: `src-tauri/target/release/bundle/macos/Truehand.app` (about 20 MB, 5 MB of it the shell) and `bundle/dmg/`. Signed ad hoc only: each new build has a new cdhash, so the first launch after an update asks once to read its Keychain item (choose "Always Allow").

## Try it without touching the real server

```sh
open -n --env TRUEHAND_SHELL_HOME=/tmp/th-home --env TRUEHAND_SHELL_ADDR=127.0.0.1:7899 src-tauri/target/release/bundle/macos/Truehand.app
```

The server then runs with `HOME=/tmp/th-home` on that port, with its own Keychain account (`test:<home>`). These two variables are read by release builds too, on purpose, so the bundle that ships is the one tried. They only choose where a new server lives: whoever can set them when launching the app can already run `truehand serve` themselves, and the shell still sends nothing to a server that fails the challenge.
